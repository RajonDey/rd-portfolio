# 2.24 Inbox shortlist cache

## Status

`done`

## Goal

After Find jobs, the Apply shortlist stays on `/desk` across reloads for up to seven days (or until the owner marks / clears those URLs). Refresh is explicit. No database.

## Why

Today each visit starts with an empty Inbox until Find jobs runs again. That is by design in `2.4` (no persistence), but the operating loop needs a stable shortlist: review, open Docs, apply by hand over hours or days. Owner review: the list should remain until applied/removed, or at least about a week. Depends on store reliability (`2.23`).

## In scope

- Persist the last successful Discover result in the same desk store as the tracker:
  - Gist file `inbox.json` when gist env is set
  - Else `.desk-out/inbox.json`
- Shape (locked): `{ savedAt: ISO string, apply: DiscoverHit[], overflow: DiscoverHit[], skipped: number, scanned: number, sourceErrors: string[] }`. Cap payload: keep at most 40 apply + 2 overflow hits already produced by discovery; do not store full JD HTML if a hit already has a long description — trim each description to 8_000 characters on write.
- On signed-in `/desk` load: if `inbox.json` exists and `savedAt` is younger than **7 days**, show that shortlist under Inbox without scanning. Older cache is ignored (treat as empty until Find jobs).
- Find jobs button becomes a refresh: running it replaces the cache. Label stays `Find jobs` when empty; when a cache is shown, also show a text action `Refresh scan` that POSTs discover and overwrites the cache.
- After a successful Tracker mark (Applied / Skip / Silence / Interview) for a URL, remove that URL from the cached inbox (same as today’s client hide), and rewrite `inbox.json`.
- `runDiscovery()` still drops tracked URLs; cached inbox must also filter tracked URLs on read so Tracker marks from another device hide rows.
- Monday weekly email stays a live scan (unchanged). Cache is for interactive `/desk` only.
- Copy, overlay one line, architecture, progress tracker, spec README.

## Out of scope

- Database, Sheets, or a second gist
- Changing discovery sources or score rules
- Auto-refresh on a timer
- Persisting Skip-reason packs or PDFs in the cache
- Google Docs workspace (`2.25`)
- Reopening `2.23` beyond using its store

## User-facing behavior

1. Sign in. If a fresh cache exists, Inbox shows last shortlist and when it was saved (date).
2. Open postings, mark Applied / Skip. Those rows leave Inbox and stay in Tracker (`2.6`/`2.23`).
3. Reload the page later the same week: remaining jobs are still there.
4. Click Refresh scan / Find jobs: new scan replaces the cache.
5. After seven days, cache is ignored until the next scan.
6. Public site unchanged.

## Open questions

- TTL: **7 days** (recommended) vs until the list is empty only? Spec locks 7 days unless owner says otherwise.
- Trim description to 8_000 chars — OK for pack regenerate from cached text? Pack still needs description; if trimmed too hard, pack quality drops. Alternative: store URL + score metadata only and re-fetch JD on pack (more fragile). **Recommendation:** keep trimmed description in cache (8_000).
