# 0.5 Work and case studies

## Status

`done`

## Goal

`/work` stays a short selected list. `/work/[slug]` is a **short article**: problem, role, constraints, outcome, and what I owned. Same template for every work URL. Copy is selected and shortened from existing `portfolio.ts` fields only. No new metrics, clients, or claims.

## Why

Current case-study pages are the old tutorial template (gradient hero, numbered process 1–4, ten feature bullets, icon rows). Hiring managers need a document, not a case-study generator. `context/portfolio-v2.md` already named Gourob-style articles. List membership is locked in `0.3`. Depends on `0.2`–`0.4`.

## In scope

- One article layout for `/work/[slug]` (case studies and project details).
- Map existing fields into that layout (table below). Trim length. Do not add facts.
- Drop process phases, feature checklists, learnings columns, next-steps, 4-column result widgets, and icon chrome from the public article.
- Optional one still image if the record already has `image`.
- Keep `/work` as a text list of the six `SELECTED_WORK_SLUGS`. You may use `subtitle` instead of the long `description` on the list when a subtitle exists.
- Unselected slugs (e.g. `enterprise-email-development-jnj`) still 200 with the **same** slim template, mapped from whatever fields they already have.
- Back link: `Work` → `/work`. Live / GitHub / demo only if the record already has those URLs.
- Server Component. `generateMetadata` already exists; keep it.

## Out of scope

- New case studies, new metrics, new quotes.
- Changing which six items are on `/work` (`0.3`).
- Home (`0.4`), `/writing` (`0.6`), `/about` (`0.7`).
- Visual system (`0.8`). No new fonts, paper color, or green pills.
- Deleting `/projects/[slug]`. It may keep the old project-detail render until `0.9`.
- Redirects (`0.2` already 308s `/case-studies` → `/work`).
- Fixing `/showcase`.

### List (`/work`)

### Article field map

Render these headings only when the mapped source is non-empty.

**Case study records** (`CaseStudy` in `portfolio.ts`):

| Heading | Source (existing fields only) |
| ------- | ----------------------------- |
| Title | `title` |
| Image | `image` (optional, one still) |
| Problem | `challenge` (may shorten; do not add) |
| Role | `role`. You may append client on the same line: `{role}. {client}.` |
| Constraints | `duration` and `teamSize` as facts. You may add up to three items from `challenges[]` if they are already there. |
| Outcome | `results[]`: show existing `value` + `metric` (and `description` if short). No new results. You may keep one short sentence from `solution` after the results, not instead of inventing numbers. |
| What I owned | `solution` (shorten). Do not paste `process[]` or `features[]`. |
| Links | `links.live`, `links.github`, `links.demo` if set |

Do **not** render: `process`, `features`, `learnings`, `nextSteps`, category chips as identity, icon rows.

**Project detail records** (`ProjectDetail`):

| Heading | Source |
| ------- | ------ |
| Title | `title` |
| Image | matching `projects[].image` if that project exists; else omit |
| Problem | omit unless you use `overview` as a single opening paragraph **instead of** a Problem heading. Prefer one `overview` block under the title, then Role. Do not invent a separate problem. |
| Role | `role`. Optional: `company` on the same line. |
| Constraints | `duration` and `team` if set |
| Outcome | `impact[]` if set, else `highlights[]`. Do not mix in new claims. |
| What I owned | `contributions[]` |
| Links | `links[]` (`label` + `url`) |
