# 2.25 Apply-docs workspace (CV + cover letter)

## Status

`done`

## Goal

Job applications use **two Google Docs** as the durable workspace: one CV doc (tabs / sections for master + variants + CB notes), one cover-letter doc (a tab or section per application). Desk links those Docs and stops treating generated PDFs as the place of record. No Google API write in this unit.

## Why

Owner review: many silent rejections; need a place to track CB (career brief / positioning) gaps; want one CV doc with tabs and one cover-letter doc with tabs instead of many PDFs. Current Desk already points at SWE / Frontend Docs (`2.12`) and can stream ATS draft + letter PDFs. Creating PDFs on demand does not bloat the git repo (they are not stored), but saving many downloads does clutter the owner’s machine and fragments the “source of truth.” A tabbed Doc workflow is cheaper, editable, and matches how the owner already applies. See `context/progress-tracker.md`.

## In scope

### Policy (overlay)

Lock in `context/job-search-profile.md`:

- **CV Doc (one file):** tabs or clear H1 sections for (1) Master, (2) SWE apply, (3) Frontend apply, (4) optional CB / positioning notes (top gaps vs target roles — owner-edited; Desk may later suggest bullets in a future LLM unit, not here). Existing Doc IDs stay unless the owner replaces them with one merged Doc.
- **Cover letter Doc (one file):** one tab (or dated H1) per company application. Desk letter PDF is a **draft to paste**, not the archive.
- Apply by hand: export PDF from the Doc when the form needs a file. Do not keep desk downloads as the library.
- Desk does **not** call Google Docs API in this unit (no OAuth, no auto-create tab). Connection = links + copy instructions.

### Desk UI

- Signed-in `/desk`: a quiet **Apply docs** block (after loop line or above Paste): links to CV Doc workspace + Cover letter Doc.
- Inbox / Paste Apply rows: keep SWE Doc / Frontend Doc links. Add one line: `Paste letter draft into the Cover letter Doc (new tab).`
- Letter download label stays; intro copy clarifies it is a draft for the Doc.
- Optional: Tracker Applied row shows the same two Doc links (no per-job deep link until API exists).

### Config

- Add `COVER_LETTER_DOC_URL` in `src/lib/site.ts` (owner pastes the Doc URL once). Overlay records the same ID.
- If the owner merges SWE+Frontend into one tabbed CV Doc later, a follow-up can collapse `SWE_CV_DOC_URL` / `FRONTEND_CV_URL`; this unit does not force a merge.

### Docs for agents

- Architecture + progress tracker + spec README.
- Explicit: no DB; no storing letter bodies in gist in this unit.

## Out of scope

- Google Docs API, service accounts, or auto-creating tabs
- LLM rewriting CB notes or letters into the Doc
- Deleting React-PDF pack routes (`2.3` stays as optional ATS draft + letter draft)
- Merging the three existing CV Docs into one (owner does that in Drive if desired)
- Inbox cache (`2.24`) and store reliability (`2.23`) beyond linking
- Weekly OS database
- Auto-apply

## User-facing behavior

1. Owner creates or names one Cover letter Google Doc; puts its URL in env / `site.ts` as locked in this spec’s open questions resolution.
2. Sign in on `/desk`. Apply docs shows CV + Cover letter links.
3. For a job: open the matching CV tab/Doc, open Cover letter Doc, add a tab (or section) named like `Company — Role — date`, paste Desk letter draft if useful, tweak, export if needed, submit on the company site.
4. Mark Applied on Tracker. PDFs in Downloads can be deleted; Docs remain the archive.
5. Public site CV button unchanged.

## Open questions

2. **CV Doc shape** — keep separate SWE + Frontend Docs (current), or merge into one Doc with tabs? Recommendation for this unit: **keep current two apply Docs + Master**; use the Cover letter Doc for tabs; add a short CB notes section inside Master (or a fourth tab) without forcing a Drive merge.

## Notes for the agent

- Do not invent Doc IDs. Wait for the cover letter URL from the owner.
- Do not scrape Google Docs.
- Do not remove `/desk/pack`; only reframe it as draft.
- Cost: Docs API would need OAuth or a service account and is not “simple”; links + tabs are the simple path. Weekly OS DB is unnecessary for this content.
