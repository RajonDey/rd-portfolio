# 2.26 Desk storage decision (gist vs DB vs Sheets)

## Status

`done`

## Goal

Lock where Desk data lives for the next stretch: secret gist (current) for tracker, notes, and inbox cache. No Weekly OS database and no Google Sheet sync unless a later pain forces it.

## Why

Owner asked whether tracker / notes / shortlist need a DB (Weekly OS), Google Sheets, or Docs. Bugs in review are explained by missing gist env and no inbox cache — not by gist being the wrong tool. Choosing once avoids rebuilding storage three times. See `2.23`–`2.25` and `context/progress-tracker.md`.

## In scope

- Decision recorded in `context/architecture.md` and the overlay:

| Data | Store | Why |
| --- | --- | --- |
| Tracker jobs | gist `tracker.json` / `.desk-out/tracker.json` | Already shipped (`2.6`/`2.7`); enough for one user |
| Usage notes | gist `feedback.json` / local file | Same (`2.17`) |
| Inbox shortlist | gist `inbox.json` / local file | `2.24` |
| CV + letters content | Google Docs (human tabs) | `2.25`; not JSON |
| Pack PDFs | Not stored | Stream only (`2.10`) |

- Explicit non-goals until revisited: Weekly OS table, Supabase, Google Sheets API, Google Docs API as a database.
- Revisit triggers (write them down): gist >400KB thrash, need multi-device conflict UI, or owner wants SQL queries over applications. Then a new spec may introduce **one** table in Weekly OS — not Sheets-as-DB.
- No application code in this unit unless a one-line architecture comment is missing after `2.23`/`2.24` land.

## Out of scope

- Implementing `2.23`–`2.25`
- Migrating existing tracker rows
- Building Sheets sync “because it is free”
- Multi-user auth

## User-facing behavior

1. Owner continues using `/desk` with gist (live) or local JSON (`next dev`).
2. CV and cover letters live in two Docs (`2.25`).
3. No new login to a database console for daily apply work.
